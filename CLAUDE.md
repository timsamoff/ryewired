# Ryewired Ã¢â‚¬â€ Project Handoff

## Mission

Ryewired is a virtual breadboard for designing, testing, and exploring analog guitar pedal circuits with an emphasis on authentic sonic behavior rather than laboratory-grade electrical simulation. Its goal is not to replicate every aspect of SPICE, but to faithfully capture how real pedals respond, clip, compress, and interact under playing conditions so builders can prototype, experiment, and compare component choices with results that sound and feel like the hardware. Wherever a tradeoff exists, Ryewired prioritizes the characteristics that most influence the listening experience while remaining grounded in accurate circuit behavior.

Every scoping decision in this project should be weighed against that statement. When two implementations are both defensible, prefer the one that moves perceived, playable realism, not the one that's more electrically complete for its own sake.

## How I want to work

**Discuss before implementing.** For anything beyond a trivial, obviously-correct fix, lay out the approach, the tradeoffs, and (where relevant) a concrete recommendation, and wait for sign-off before writing code. This isn't a formality, real design decisions in this project have gone back and forth multiple times (see "Decisions that got revisited" below), and premature implementation has cost real rework more than once.

**One task at a time.** Don't bundle unrelated fixes into one pass. If investigating one thing surfaces a second, real, unrelated bug, say so and ask whether to fix it now or note it for later, don't just fix it silently alongside the original task.

**Surgical fixes over rewrites.** Prefer the smallest change that correctly addresses the root cause. Don't refactor adjacent code "while you're in there" unless asked.

**Verify, don't just reason.** This codebase has repeatedly punished confident-but-unverified claims (see "Verification technique" below, and the section on things that turned out wrong). When a claim is checkable Ã¢â‚¬â€ "does this function get called," "does this value ever exceed X," "does the bug reproduce" Ã¢â‚¬â€ check it before asserting it, ideally by actually running the real code against real data, not by reading it and reasoning about what it should do.

**When I push back, take it seriously and re-derive, don't just re-assert.** More than once in this project, a "walk me through the causal chain" or "show me the actual numbers" request has caught a real overreach in an otherwise-plausible-sounding diagnosis. Treat pushback as a request to actually re-derive the claim, not as something to politely defend.

**Own mistakes plainly.** When a fix turns out to be wrong, or a claim turns out to be an overcorrection, or a regression gets introduced, say so directly and explain what actually happened, don't downplay it or bury it in the next fix's explanation.

## Architecture

Vanilla JS, zero external dependencies, no build step. The main app is web-only (never Electron). A separate admin tool for managing component definitions is intentionally Electron, that's fine, it's not the main app.

**Files**: `js/simulation.js` (DC solver Ã¢â‚¬â€ nodal analysis, BJT/diode companion models, battery/sag), `js/audio-engine.js` (builds the actual Web Audio graph by walking the netlist; gain/clipping math derived from the DC solver's output), `js/board.js` (canvas rendering, drag/drop, wiring), `js/shapes.js` (component visual rendering), `js/properties-panel.js` (the properties UI), `js/components-registry.js` (component instantiation, defaults, tolerance resolution), `js/workbench-strip.js` (permanent Power/Input/Output devices), `js/app.js` (init, event wiring, global helpers), `data/components/*.json` (component schemas + model_params).

**Board geometry**: rows 5-9 are the top half, 0-4 are the bottom half (non-sequential). Rail rows are string keys (`'rtp'/'rtm'/'rbp'/'rbm'`). Row lettering is per-half. Columns ascend right-to-left. **Both power rails span the full board width as one continuous electrical segment** Ã¢â‚¬â€ there used to be a deliberate break at column 31 (mimicking a real breadboard), it was removed later in the project; if you see any reference to a rail break or `RAIL_BREAK` anywhere, that's stale, it shouldn't exist in the codebase anymore.

**Net model** (`buildNetMap` in simulation.js): union-find over row/column bonding (columns bond rows 0-4 together and 5-9 together, mimicking a breadboard's 5-hole strips) plus wires plus closed switches. A component's own two legs are *never* unioned to each other, only physically-identical-node connections bond.

**Stage gains come from a SMALL-SIGNAL NETWORK SOLVE, not per-component formulas.** `solveSmallSignal` in simulation.js runs every tick after the DC pass, reusing the same nodal machinery with the supply rail as AC ground, coupling caps as shorts, transistors as hybrid-pi (r_pi = hFE/gm, plus a gm*Vbe source), and the input net driven at 1V Ã¢â‚¬â€ so every solved node voltage IS that node's gain relative to the input. `audio-engine`'s `netGain(a,b)` reads the ratio between two nets, and that ratio is the gain of whatever sits between them, feedback and loading included.

Three consequences worth protecting. **Feedback works**, because a nodal solve doesn't care that the netlist has loops (a Fuzz Face's collector-to-base resistor finally changes Q1's gain when the Fuzz pot moves). **Loading works** (a 10k vs 1M volume pot now changes the driving stage's gain 7.2 vs 20.4; it used to change nothing). And **a potentiometer is modelled exactly once**, in the solver, as two resistors and a tap Ã¢â‚¬â€ volume, tone, fuzz, time, repeats all emerge from what it's wired to. Do not add a per-use-case pot rule back; that's what `gain = wiper fraction` was, and it made pot resistance irrelevant.

**BJT leakage (ICBO) is stamped collector-to-base, and that is deliberate.** The solver stamps raw ICBO as a current source from collector to base, then lets the solve decide how much of it gets amplified: leakage arriving at the base splits between the base network and the B-E junction, and whatever reaches the junction is amplified by the existing gm stamp. Do NOT "simplify" this back to pre-multiplying by `(hFE+1)` and stamping collector-to-emitter. That form is the ICEO case, meaning base OPEN, which is the maximum possible multiplication rather than the general one, and applying it unconditionally made realistic germanium ICBO values unusable (see "Things that turned out wrong"). Base open still produces `(hFE+1)*ICBO` under the current model, but as an emergent result of the netlist rather than an assumption. Per-model `vce_sat` is likewise read per transistor, not from a global constant, since germanium saturates at roughly half silicon's Vce(sat).

**Every clipping WaveShaper runs at `oversample = '4x'`** (`CLIP_OVERSAMPLE`). The property defaults to `'none'`, and a hard nonlinearity at 1x folds its out-of-band harmonics back into the audible range as inharmonic "digital fizz". Measured at 16-21dB of folded energy on the Fuzz Face before this. Don't remove it, and set it on any new WaveShaper.

**Two board-level checks run every tick, before the numbers are trusted**: a structural floating-terminal check on the net map (a transistor/diode/LED leg alone on its net), and a supply-range sanity check on solved node voltages (nothing can legitimately sit outside the rails in a DC-only resistive model). Both report through the same `failBoard` channel as the supply-conflict check. Keep BOTH: they catch the same class of fault by different means, and which one fires depends on whether the broken part happens to saturate.

**The audio model is fundamentally**: solve the real DC operating point with the actual nodal-analysis solver (not a toy approximation), then linearize each transistor stage around that point to build a Web Audio graph (gain node + WaveShaper per stage). This is *not* a full SPICE-style transient solve, that tradeoff has been discussed and explicitly declined twice this project (see below), it's not the direction to reopen without a very good reason.

**Live changes while playing come in two kinds, and they take different paths.** *Value* changes push onto the existing graph without rebuilding anything: `updateLiveGains` (wired to `Simulation.onUpdate`, so every 10ms tick) rewrites transistor gain and clip curves, and `updatePotWiper` ramps a pot's gain node. *Topology* changes need the net-graph walk re-run, via `AudioEngine.refreshTopology` (wired to `Simulation.onTopologyChange`). Editing is locked while the circuit is engaged, so the only topology change that can happen mid-play is a switch toggling, which is deliberately exempt from that lock because a switch is a runtime control rather than an edit. `refreshTopology` rebuilds only the walk's nodes and never `_source`, so an audio file mid-playback isn't restarted by flipping a switch. Ordering matters: the DC re-solve must run before the rebuild, or every transistor stage gets built from the pre-toggle operating point. If you ever add another mid-play topology change, it goes through `onTopologyChange`, not `onUpdate`, which fires 100 times a second.

## Verification technique (use this constantly)

For anything solver-related, don't just read the code and reason about it, extract the real functions (`buildNetMap`, `solveNetVoltages`, etc.) into a Node test harness, stub `Board`/`WorkbenchStrip`/`ComponentRegistry`/`Utils` as globals, load `simulation.js` via `vm.runInContext` (bind the sandbox's `Simulation` to something reachable Ã¢â‚¬â€ top-level `const` in a vm sandbox does not attach to the sandbox object by default, append `;globalThis.Simulation = Simulation;` to the loaded source to make it reachable), and run it against real `.rw` files with modified property values. This has repeatedly produced real, verifiable answers (exact voltages, which specific component fails, leg-to-net mapping) instead of confident-sounding guesses that turned out wrong. Use a **fresh `vm.createContext` per run** if comparing multiple scenarios in one script, reusing one sandbox across runs can leak state between them.

**For "it doesn't sound right", render and measure the graph offline rather than reasoning about which feature is missing.** The audio graph is a handful of GainNodes, WaveShapers and BiquadFilters, all of which are a few lines to reimplement in Node (biquads are the RBJ cookbook formulas the Web Audio spec specifies; WaveShaper is a linear interpolation across the curve). Capture the real graph from `traceSignalPath` with an instrumented fake context, topologically order it, and run signals through it. That turns vague complaints into numbers:

- **Frequency response**: sweep sines at an amplitude too small to clip, measure output RMS per frequency. Finds filters that are in the wrong place. This is how the 50x coupling-cap error was confirmed and how "missing low end" was disproved (the bass was flat to 30Hz; the problem was elsewhere).
- **Harmonic content**: a sine at a musical fundamental, then a DFT at each harmonic. H2-dominant means asymmetric clipping (even harmonics, warmth), H3-dominant means symmetric (odd, square). Quantifies "not distorted enough" as an actual THD number and an actual onset threshold.
- **Aliasing**: drive a HIGH sine (3-7kHz) into the clippers and measure energy BELOW the fundamental. A memoryless nonlinearity can only generate harmonics ABOVE the fundamental, so anything underneath it is folded-back aliasing and nothing else. Clean, unambiguous test.

**Drive it from real `.rw` files, not hand-built netlists.** A harness that loads an actual saved file, dumps the resolved netlist (every component leg to its net), flags nets with only one thing on them, prints the DC operating point per transistor, and reports whether the audio walk reaches the output, answers "what is this circuit actually doing" in one run. Sweeping a named pot across its range and printing the resulting gain in dB turns "the knob feels like it does nothing" into a number. Both were decisive on a real user circuit where reasoning from the schematic would have been wrong: the file's netlist did not match the schematic it was built from. Note the board geometry when reading a file by hand Ã¢â‚¬â€ rows 5-9 are one half and 0-4 the other, so the same column in different halves is a DIFFERENT net.

**The same technique works on `audio-engine.js`, with three extra pieces.** The `globalThis.AudioEngine = AudioEngine;` append is needed for the same reason as `Simulation`. Functions that live *inside* the IIFE (`traceSignalPath`, `signalLegPairs`, and anything else not on the returned object) can't be reached that way at all, since appending after the file is outside the closure: string-replace the `return {` block to inject `globalThis.__x = theFunction;` just before it, and assert the marker was found so the harness fails loudly if the return block ever changes shape. Then stub a fake `AudioContext` (`createGain`/`createBiquadFilter`/`createWaveShaper`/`createAnalyser`/`createConstantSource`, each returning a node with `connect`/`disconnect`), expose it as `window.AudioContext`, and stub `setInterval`/`clearInterval` since the vm sandbox has no timers. Have the fake `connect()` record `[from, to]` edges: a BFS over those edges is an *independent* check of whether audio really reaches the output, rather than trusting the walk's own `reachedOutput` flag. That distinction has already caught a harness bug that a flag-only assertion would have passed.

## Decisions that got revisited (don't re-litigate without new information)

- **The rail break was removed.** It existed deliberately (mimicking a real breadboard's physical break), was reconsidered and explicitly kept once, then later reversed for good Ã¢â‚¬â€ after it caused a real, reproduced bug (a simple voltage divider reading 9V at every junction because the ground wire landed on the disconnected side of the break relative to where the power supply's real dynamic connection point is). Both rails now span the full width. Don't reintroduce a break without being asked.
- **Dynamic re-linearization is block-rate, not per-sample.** A full nonlinear transient solve (true SPICE-style, Newton-Raphson per audio sample) was proposed twice, once via an imported WASM SPICE engine (`ngspice-js`/`jsWebSPICE`), once via a from-scratch custom transient solver, and declined both times for the same reason: it's a fundamentally bigger, differently-shaped project than a vanilla-JS, no-build-step, browser-main-thread app can reasonably support, and it would mean setting aside the hand-tuned, extensively-debugged existing solver. The chosen direction instead: re-run the *existing* DC solver periodically (piggybacking on the existing 10ms `Simulation.tick()` loop) using a tracked instantaneous signal level, and push updated values onto an *already-built* Web Audio graph rather than rebuilding it. Don't reopen the "should this be a real transient solver" question without a genuinely new constraint.
- **Amp/speaker/cabinet simulation is out of scope.** Ryewired's job is to get the pedal circuit right, given realistic boundary conditions (input source impedance, output load impedance Ã¢â‚¬â€ see "Open work" below). Modeling what's downstream of the pedal is a different, much bigger project.
- **Tone stacks don't need op-amps, and the real blocker is impedance modeling.** An earlier note here said tone stacks were premature because no op-amp component exists to host one. That reasoning was wrong: the Big Muff tone control is entirely passive, one pot plus two resistors and two caps, no active device involved. The actual blocker is item 8 in Open work. A passive tone stack is two interacting frequency-dependent branches blended by a pot, and the current signal-level audio graph structurally cannot represent that: `buildAudioStage` only recognizes one hardcoded shape ("resistor with a cap shunting to ground") as a lowpass, and treats a series cap as a fixed-reference highpass. Revisit once the audio graph derives impedance from the netlist, not once op-amps exist.
- **The root Electron wrapper was deleted.** The repo root used to carry a `main.js`/`preload.js` Electron app alongside the admin tool's own, so the main app shipped as both web and desktop. It was removed because it had already stopped working: every menu item sent an IPC message (`menu:save`, `menu:undo`, and so on) that no renderer code listened for, and the `window.api` bridge preload exposed had zero consumers (components load via `fetch`, saving uses `showSaveFilePicker` with a download fallback). The root `package.json` now has no dependencies at all. Don't reintroduce a desktop wrapper for the main app; the admin tool staying Electron is separate and fine.

## Open work, roughly in priority order

1. **Confirm the dynamic re-linearization + tolerance work actually holds up in-browser.** Partly unblocked now: a scope bug was silently disabling `_vceHeadroom` entirely (see "Things that turned out wrong"), so before it was fixed, clip headroom was pinned at its maximum and could not respond to bias, sag, or supply voltage at all. With that fixed, `_vceHeadroom` verifiably differentiates by transistor (a 2N3904 and a 2N5088 in the same stage land at 1.0 vs 0.0003, so clip headroom 0.9 vs 0.15). Still to confirm by ear in-browser: does changing a transistor's gain/leakage audibly change the sound, and does battery sag respond to how hard the input is played. This is now finally testable: the reference Fuzz Face was itself miswired (Q2 one column off, leaving its collector floating) and separately mis-biased by the leakage model, so every earlier listening test was judging a broken circuit. It now biases to Q2 Vc around 4.4-4.9V with a working Fuzz control. **Listen before building anything else** Ã¢â‚¬â€ the remaining open items branch on whether it now sounds right.
2. **The gain knee is a single tradeoff dial between two circuits, and no value satisfies both.** `kneePoint` now equals `maxGain` (35), the only value with no systematic gain error, and the Electra/LPB-1/Fuzz Face all sound right at it. But measured across the sweep, Electra THD at input 0.1 versus the Fuzz Face's Fuzz-pot swing runs 27.5%/0.02dB at knee 35, 3.9%/0.47dB at 200, and 1.0%/3.20dB at 400. Strictly opposed, no compromise value. The mechanism: once a memoryless limiter saturates, changing the gain feeding it changes nothing, so with accurate (high) gain every stage is pinned and downstream controls go inert. **Do not try to "fix" the Fuzz pot by retuning kneePoint** Ã¢â‚¬â€ it only trades one circuit against the other. The fix is item 7 (feedback) plus the dynamic-relinearization brief.
3. **Supply voltage may not move the clipping point, and the reason is structural.** `headroomRef = 3 * (activeSupplyV/9)` in simulation.js scales linearly with supply, but in a fixed-base-bias stage Vce also scales roughly linearly with supply, so the ratio cancels and `_vceHeadroom` comes out identical at 9V, 6V, 4.5V and 3V. Measured, not reasoned. This does NOT necessarily generalize: the test used fixed-base bias, and a Fuzz Face uses collector-feedback bias where the relationship differs. Worth checking against a real circuit topology before concluding the formula is wrong, since the cancellation may be physically correct (a fixed-base stage genuinely does scale its whole operating point with supply).
4. **Asymmetric clipping: DONE, for diodes and transistors, both derived rather than tuned.** A transistor stage's two clip thresholds are now its REAL output swing in volts, per direction, from `setOutputSwing` in simulation.js: `_swingDown` = how far the collector can fall to Ve+Vce_sat, `_swingUp` = how far it can rise to the rail. These differ a lot in practice and that asymmetry is the even-harmonic character (a Fuzz Face Q1 measures +1.39V/-7.41V, Q2 +0.53V/-7.41V). Two things this depends on, don't undo either: `makeClipCurve` now ASYMPTOTES to its threshold (`t*tanh(x/t)`) instead of the old `t+(1-t)*tanh(...)` which saturated at 1.0 whatever t was, so t only set the knee and not the limit; and the BJT stage is pre-scaled into the shaper's [-1,1] domain and post-scaled back out, because a real swing of several volts doesn't fit in it. Curve resolution went 256 -> 4096 for the same reason. **The old normalized `0.15 + 0.75*vceHeadroom` threshold was dimensionally incoherent** Ã¢â‚¬â€ a 0-1 number sitting in a path whose gains are real volts-per-volt.
5. **The Fuzz control cannot be fixed inside the static model. Stop trying.** Measured four separate ways, all negative: removing the gain knee entirely (0.01dB of swing), adding asymmetric transistor clipping (0.01dB), giving the clip thresholds real voltage meaning (0.02dB), and modelling feedback via the small-signal solve (0.02dB, even though the solve correctly moves Q1's gain 344 -> 266 as the knob turns). It only becomes audible below roughly input amplitude 0.01, where the circuit stops saturating: at 0.01 it moves THD 13.4% -> 26.5%, at 0.003 it gives 5.9dB of swing. The app's default input (amplitude 1, halved by `buildSource`) drives at 0.5, which is 10-50x past every clip threshold. **No static curve can fix this**: a memoryless nonlinearity above saturation emits the same waveform whatever the drive, so the information the knob carries is destroyed before it reaches the output. Only a moving operating point carries it, which is the dynamic-relinearization brief. Note a real Fuzz Face is genuinely saturated at full guitar output too; what makes its knob work there is bias shifting under signal.
6. **Input/output impedance.** Input is currently an ideal, zero-impedance voltage source; Output has no load impedance. Neither exists in real life, and this matters for pedal-to-pedal and pedal-to-amp interactivity (a Fuzz Face has no output buffer and is famously sensitive to what's downstream). No inductor component exists yet, so a proper pickup model needs one (or ships as a resistor-only approximation first). **Note this item used to also claim "lacks low-end heaviness" as its symptom. That was wrong** Ã¢â‚¬â€ that turned out to be the hardcoded coupling-cap reference impedance in item 9, which was filtering up to 50x too high. Don't re-attribute a tonal complaint here without measuring first.
7. **Feedback is now modelled, but saturation still hides it.** The audio *graph* is still a DAG (Web Audio can't do zero-delay feedback), but stage gains no longer come from that graph's topology Ã¢â‚¬â€ they come from `solveSmallSignal`, where loops are fine. A Fuzz Face's 100k does participate now: sweeping the Fuzz pot moves Q1's solved gain 344 -> 266, which never happened before. **The knob is still audibly inert (0.02 dB)**, because every stage is saturated and changing the gain feeding a slammed limiter changes nothing. So this item is no longer the blocker; item 2 (saturation) and the dynamic-relinearization brief are. Don't re-diagnose the Fuzz pot as a feedback problem Ã¢â‚¬â€ measure the saturation first.
8. **The audio graph is signal-level, not impedance-aware.** `traceSignalPath` *is* branch-aware (an older note here claiming a single primary-path walk was stale). Every reached net gets its own bus, so several components on one net each get connected and Web Audio sums them.

   **Shunt CLIPPERS are now handled properly**: a diode or LED from a net to ground is detected up front and becomes a clamp on that net (the net gets an in-node and an out-node with a WaveShaper between, so everything downstream hears the limited waveform), rather than a series hop into the nulled ground bus where it was silently inaudible. Do not "simplify" that back into an ordinary hop. Nets without a clamp still get a single node used for both directions, so circuits with no shunt clipper build exactly the graph they did before.

   **The eventual fix for items 6, 7, 8 and 10 is one thing: a small-signal AC solve.** The DC solver already linearizes every part around its operating point; an AC version stamping complex admittances (capacitor jwC, transistor small-signal model) into the same matrix and solving at a set of frequencies would yield the real input-to-output transfer function, with feedback loops, impedance, loading and coupling corners all falling out of it instead of being pattern-matched shape by shape. The audio graph then becomes that response plus the nonlinear clipping stages. Don't build any more per-shape helpers without weighing this first.

   Still NOT modeled: impedance generally. A shunt-to-ground *capacitor* next to a series resistor doesn't steal high frequencies from the series path (that one case is special-cased in `buildAudioStage` as a combined lowpass, which is a special case rather than a model), source impedance doesn't affect how hard a clamp bites, and a series cap still uses a fixed 10k reference (item 9). This is the honest remaining limitation and it overlaps with item 6.
9. **Coupling-cap corner frequencies: fixed, and this was never "minor".** A series cap's corner now comes from `acLoadResistance()` walking the netlist for the real source and load impedance (resistor to AC ground, pot track to AC ground, or a transistor base at hFE*(re+Re)), summed as source + load. AC ground means the ground rail OR the supply rail, since a supply is a low impedance at signal frequencies. When nothing is recognisable it falls back to 10kÃŽÂ© **and warns by name**, because the silent version of exactly this fallback is what hid the bug. Measured before and after: Fuzz Face output cap 1591.5Hz -> 31.8Hz, Electra output 159.2Hz -> 10.8Hz, Electra input 159.2Hz -> 17.8Hz. What remains is that `acLoadResistance` pattern-matches three shapes rather than solving the network, same structural weakness as `findEmitterResistance` (item 10) and the same eventual fix as item 8.
10. **RESOLVED Ã¢â‚¬â€ `findEmitterResistance` is deleted.** Emitter degeneration now falls out of the small-signal solve, so there is nothing left to pattern-match and no silent zero to mistake for "no emitter resistance". The only remaining shape-matcher is `acLoadResistance`, used for coupling-cap corners, and its transistor branch now recurses into itself (depth-guarded) rather than calling a second matcher. Kept below for the record: it *pattern-matched two hardcoded topologies and returned 0 for everything else**, which is indistinguishable from "this stage genuinely has no emitter resistance." A pot wired even slightly differently from the one shape it recognises makes the knob silently inert with no warning anywhere. This cost a full debugging session on a real Fuzz Face. At minimum it should warn when a pot sits on a transistor's emitter net in an unrecognised configuration; properly, it should derive emitter impedance from the netlist instead of matching shapes, which is the same underlying gap as item 8.
11. **Small known bugs, each roughly one line**: `solveNetVoltages`'s potentiometer branch uses `parseFloat(inst.props.wiper) ?? 0.5`, and `??` does not catch NaN, so a missing wiper poisons the whole conductance matrix (the same hazard was deliberately fixed with `Number.isNaN` in three other places and missed here). `getLayoutData` strips `_voltage`/`_current`/`_state`/etc but NOT `_vceHeadroom`, `_saturated`, `_rLow`, `_rHigh`, so stale runtime state is written into saved `.rw` files and reloaded. `hasElectricalPath` is exported but has no callers.
12. **ICBO of exactly zero is a discontinuity.** With leakage at 0 the Fuzz Face solves to a saturated Q1 at Vc 8.13V, while 0.5uA solves to a healthy circuit. Physical (no explosion, no failure trip) but it looks like the relaxation loop settling into an odd state rather than real behavior. Low priority since no real transistor has zero leakage.
13. **Queued components**, each wants its own scoping conversation before implementation: MOSFET/JFET (2N7000, J201), Zener diodes, general op-amps (TL072/LM741/LM308/JRC4558), PT2399 delay chip, LDR/vactrol for tremolo-vibrato.
14. **Parked, low priority**: cleaning up one specific saved Fuzz Face `.rw` file's visual layout (works electrically, just messy to look at).

## Things that turned out wrong, and why (worth knowing before repeating them)

- **A recalibration introduced a silent regression, and this document then described it as fixed while it was still live.** Fixing BJT headroom to scale with actual supply voltage (instead of a flat hardcoded reference) referenced a variable (`activeSupplyV`) that was declared in `tick()` but used inside a separate, non-nested function (`solveComponent`) that never had closure access to it. The resulting `ReferenceError` was silently swallowed by a `try/catch` around the call site, meaning `_vceHeadroom` was never assigned at all (so audio-engine's `?? 1` fallback pinned clip headroom at its 0.9 maximum forever) and the BJT over-current failure check never ran. It is now genuinely fixed: `_activeSupplyV` is module-scope, alongside the other tick-computed state. Two lessons. When adding a new variable to a large function, verify the place you're using it is actually lexically nested inside where you declared it, don't assume based on file proximity. And a `catch` that only logs will hide a per-tick `ReferenceError` indefinitely; when a value is mysteriously frozen, check the console for a repeating warning before theorising about the model.
- **An electrolytic capacitor rendering bug caused a real misdiagnosis.** The visual polarity stripe was always drawn on a fixed side regardless of actual leg/polarity data, for every electrolytic cap in the app, for its entire history. This led to confidently telling the user a specific capacitor was wired correctly when it wasn't (and, separately, a real wiring mistake in one saved file that the rendering bug was masking). The user's own screenshots, not code-reading, is what surfaced it. Lesson: when a user describes something visual that contradicts a code-level conclusion, prioritize getting a screenshot over re-asserting the code-level read.
- **A "fix the symptom" diagnosis skipped root-causing.** Given three vague symptoms ("transistor swaps barely change sound," "supply voltage barely matters," "lacks low-end heaviness"), the first instinct was to propose a curve-shape fix (asymmetric/exponential clipping). Asked to walk the actual causal chain per-symptom, it became clear the curve is memoryless and structurally cannot explain a frequency-dependent symptom at all, and the other two symptoms traced to an upstream gain-formula masking bug, not a downstream curve-shape problem. Lesson: for "the audio doesn't sound right" reports, trace the actual signal-flow/data-flow chain per symptom before proposing a fix, rather than pattern-matching to "what usually causes this kind of complaint."
- **A third-party AI-generated critique document contained confident, checkable claims that were wrong or stale.** One flagged an already-fixed problem using the old code's comment as if it still applied, and proposed a "fix" that would have been a measurable regression (a hard gain clamp, which flattens differentiation *harder* than the soft knee it wanted to replace). Another was internally self-contradictory (claimed a behavior was missing, then said "this is handled" in the very next sentence). Two of the eight claims were real and previously uncaught. Lesson: when evaluating any external critique or generated analysis of this codebase, verify each checkable claim against the real code before agreeing or disagreeing with any of it, don't take confident phrasing as a proxy for correctness, positive or negative.
- **This document's own "confirmed bug" description was wrong, and its proposed fix would have created the bug it described.** It stated that switches were invisible to the audio graph because `signalLegPairs()` has no `switch_spst` case, so signal would dead-end at any placed switch, and that the fix belonged in `signalLegPairs()`. Measured with a harness, the switch already worked correctly in both states: `buildNetMap` unions a *closed* switch's two legs into one net, and `traceSignalPath` uses that same net map, so a closed switch is transparent for free and an open one correctly stops the walk. Adding the proposed leg pair would have made an OPEN switch pass signal, since an open switch's legs are the only case where the two nets differ. The real gap was different and narrower: the graph is built once at Play, so toggling a switch mid-playback changed the DC solve and the visuals but not the sound (fixed via `AudioEngine.refreshTopology`). Lesson: treat this file's own bug descriptions as claims to verify, not as findings. Two separate entries here were stale or wrong when checked.
- **Nearly built an elaborate wrong fix for a symptom that had a one-line cause.** "Still missing a little low end" on the Fuzz Face led to a proposal to model transistor treble rolloff via Miller capacitance. Partway into it two problems appeared: the model data has no Ccb/ft to work from (so the numbers would have been invented), and the dominant treble rolloff in a real Fuzz Face rig isn't inside the pedal at all, it's the guitar pickup and cable interacting with the pedal's low input impedance, which is open item 6 and needs an inductor model. Measuring instead showed the bass was already flat to 30Hz and the actual defect was 16-21dB of aliasing from un-oversampled WaveShapers, fixed by setting a property that had been defaulting to `'none'`. Lesson: "sounds thin" does not reliably mean "bass is missing" Ã¢â‚¬â€ it can equally mean "there is garbage up top". Measure the spectrum before choosing which end to work on, and when a fix requires inventing datasheet values that aren't in the model data, treat that as a signal the mechanism hasn't been established yet.
- **A placeholder constant sat in the signal path for a long time and got blamed on something else.** Coupling-cap corner frequencies were computed against a hardcoded 10kÃŽÂ©. For a Fuzz Face's 10nF into its 500kÃŽÂ© volume pot that put the highpass at 1592Hz instead of ~32Hz, a 50x error removing every fundamental a guitar produces and passing only harmonics. The resulting thin sound was recorded in this file for a long time as "lacks low-end heaviness" and attributed to unmodelled input/output impedance, which sent at least one investigation down the wrong path. It was found only by dumping every node the audio graph actually builds with its real parameters, rather than reasoning about which feature was missing. Two lessons. A hardcoded stand-in inside a signal path is a bug with a timer on it, so make it derive its value or make it warn. And when a tonal complaint has been sitting in the open-work list for a while, measure the graph before theorising about which unimplemented feature would fix it Ã¢â‚¬â€ the answer was a constant that was already there, not a feature that wasn't.
- **A whole component's effect can be built, fed, and still be inaudible.** The Electra Distortion's two clipping diodes shunt the signal node to ground. `traceSignalPath` models every part as a series hop (entry bus, stage, exit bus), so both diodes were built with the GROUND bus as their exit, and the ground tap is deliberately nulled. They were reached from the source, they had real clip curves, and nothing they produced could reach the output, while the through-signal walked straight past them to the volume pot. The pedal is *mostly* those diodes, so it sounded like a clean boost. Nothing errored, nothing warned, and the netlist was completely correct. Lesson: "the stage got built" is not evidence it does anything. For an audio graph the question is whether a node lies on a path from source to output, which is a reachability check worth running (`check-clipping.js`-style) rather than assuming.
- **A textbook formula applied outside the conditions it holds under.** BJT leakage was modeled as `Ic += (hFE+1)*ICBO`, stamped collector-to-emitter. That formula is real, but it is the ICEO case: base OPEN. In an actual circuit the base is not open, so most collector-base leakage drains through the base network instead of being amplified, and true multiplication runs from about 1x (base shorted to emitter) up to `(hFE+1)x` (base open) depending on base circuit impedance. Applying the base-open maximum to every transistor in every circuit made germanium unusable: a correctly-wired Fuzz Face at 5uA on both parts had BOTH collector currents pinned at exactly `(hFE+1)*ICBO` with the bias network contributing nothing, and 10uA or more drove the collector to a non-physical negative voltage, while real builders run these parts at 50-150uA. Fixed by stamping raw ICBO collector-to-base and letting the solve distribute it. Lesson: when a formula produces results that contradict what the hardware actually does, check what conditions the formula assumes before doubting the hardware. The arithmetic was right and the premise was wrong.
- **Fixing the model changed the symptom, and silently broke a detector that had been verified working.** A supply-range check on solved voltages caught a floating transistor collector, because the node exploded to about 1e9 volts (the solver's tiny EPS leak-to-ground being the only path to ground). After the ICBO fix the same broken board saturated instead, the saturation clamp tied the collector to the emitter through RSAT, the voltage read a perfectly ordinary 0.2V, and the check went silent while current was still reported through a leg connected to nothing. Caught only because the broken file was re-run after the model change. Lesson: a check that keys on a SYMPTOM is only valid for as long as the symptom is; prefer checking structure (is this leg connected to anything) over checking consequences (did the number blow up), and re-run your known-bad cases after any model change, not just the known-good ones.
- **Two representations of one piece of state, OR'd together.** `Utils.isSwitchClosed` read `!!inst._state || inst.props.state === 'Closed'`, where `props.state` was a user-editable dropdown and `_state` was the runtime toggle. That broke three ways at once: setting the dropdown to Closed pinned the switch shut permanently (the OR meant flipping `_state` could never open it), and because `getLayoutData` strips `_state`, a toggle survived neither save/reload nor undo/redo. Fixed by making `props.state` the single source of truth that the toggle writes. Lesson: when runtime state and a serialized property describe the same thing, one of them has to be authoritative; combining them with `||` silently makes the sticky one win and quietly drops the other from anything that serializes.
- **A units conversion bug (nA vs Ã‚ÂµA) produced a wildly incorrect leakage value that looked like a different bug entirely** (a resistor failure that seemed backwards from what the underlying physics predicted). Traced to a value being typed into a field while the wrong unit was selected in its dropdown. Lesson: when a numeric-property change produces a wildly disproportionate effect, check which unit was actually selected before assuming the underlying model is wrong.

## Style notes

No em dashes in writing. Plain, direct, declarative technical prose, explain the reasoning, not just the conclusion. When something is uncertain or provisional (a calibration constant, an unverified assumption), say so explicitly rather than presenting it with more confidence than it's earned.
